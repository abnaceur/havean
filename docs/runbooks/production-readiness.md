# Production readiness

The local Compose file is development-only. A production release requires the remaining Q tasks and provider checks; check:release must pass before signoff.

Configure actual domains, HTTPS, separate identity/storage/search secrets, production OIDC registration and recovery mail, staff OTP/WebAuthn policies, licensed map/geocoder providers, malware scanning, mail/SMS delivery and production inventory rights. Replace demo realms/personas and remove synthetic inventory explicitly through a reviewed importer.

Use immutable application image digests, separate migration and runtime credentials, private infrastructure networks and TLS at the reverse proxy. Do not use Keycloak start-dev in production. Set secure cookie behavior, staff MFA claim mapping and trusted origins. Scope provider credentials to individual buckets, and sign private downloads with short expirations.

Before launch: source financial reconciliation, cross-organization denial tests, complete reference/accessibility review, actual capacity measurements, dependency/container security scans, isolated restore rehearsal, identity/object backup verification, RPO/RTO measurement and schema-compatible rollback rehearsal. A previous application image does not undo a schema migration.

The API denies staff actions in production unless the verified access token's `acr` is at least 2. Configure the Keycloak browser flow to require OTP or WebAuthn for staff and map that flow to level 2; never map password-only authentication to that level. The operations login requests `acr_values=2`. Generated local realms include real staff OTP credentials; password-only development authentication cannot supply production staff MFA. Production boot rejects HTTP origins and `DEV_PASSWORD`.

## Verified local packaging and release boundaries

Use `compose.production.yaml` and `infra/Dockerfile.production` for compiled Node and Next standalone images. Protected staging configuration is generated by `scripts/staging-setup.mjs`; immutable application IDs are required before startup. See [launch handoff](launch-handoff.md), [recovery](backup-restore.md) and [application rollback](application-rollback.md).

The original 33 English baselines, nine D08 updates and 21 changed Q02 screens have recorded approval; all 34 final visual checks pass. The 29 unavailable original-site states remain V. Approval of local screenshots does not establish exact reference parity.

The Q08 HTTPS stack, Q09 local physical recovery and Q10 populated upgrade/previous API rollback have measured P evidence. Local recovery does not satisfy off-host backup acceptance. Production deployment is deferred by the user; a main-branch push is not a production launch. Release readiness additionally requires complete task acceptance and successful tests from the exact release revision.

Before a database upgrade, the extension owner must run `infra/geometry-hardening.sql` against the application database with ON_ERROR_STOP. It denies runtime decoders and preserves only the separate trusted migrator’s maintenance grant option; do not run this preflight with the application connection. SQL 165 fails if the unprivileged runtime can still execute unused FlatGeobuf decoders. Fresh Compose databases execute the same owner hardening after extension creation. PostgreSQL Debian-to-Alpine changes require a new cluster and logical dump/restore; never attach the old physical volume to the new libc image. Preserve the old database until full financial/identity/media reconciliation and application verification pass.
