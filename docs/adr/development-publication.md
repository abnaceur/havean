# Development publication and scoped sales workspace

Project publication has a separate private review record. Newly created projects are draft. Developer submission locks the owned project, checks its version, complete overview and a published type for on-sale requests, records actor/desired sales status and withdraws public eligibility while review is pending. A moderator/admin must independently inspect current facts, type ranges/inventory and publishing authority, provide a verified decision/reason and match both project and review versions. Self-review and review by the developer organization are prohibited. Rejection retains a visible private reason and allows resubmission. Approval publishes the requested coming-soon/on-sale status atomically with audit/outbox. Network retries are deduplicated.

SQL prohibits publishing an unapproved new project or forging an approval as a developer. Changes to core project facts and authored phases/buildings/type facts reset review and withdraw publication. Derived individual-unit availability changes after approval preserve approval but bump project version/time. Changes during a submitted review invalidate its snapshot, permitting resubmission and preventing a stale approval. Approved media updates continue through the independent media workflow. An obsolete pending review cannot become permanently stuck behind a changed inventory version.

Existing local published inventory is explicitly recorded as legacy_published, with a reason saying independent project approval is not claimed. This state is restricted to database schema-owner bootstrap import. Cold deterministic fixtures are inserted as draft, populated, and explicitly labelled legacy before applying their historical sales status. New API-authored fixtures use the real submission/independent-review workflow. No historical project approval is invented.

The developer workspace includes publication/status/rejection feedback, requested sales status, versioned inventory forms and a bounded project lead queue. Leads display project, selected type, general/available-unit intent, contact and workflow stage. Owner project scope and lead RLS prevent cross-developer reads/edits; stale versions fail. The existing professional status editor also refuses bypassing publication review, and recorded amounts show their actual basis.

O: existing public development navigation/cards. R: specification N05 permissions, moderation and concurrency requirements. P: private developer/moderator workspace, local synthetic inventory and test approvals. V: original private developer interface and actual production inventory/authority; no exact visual parity or production provider verification claimed.

Canonical building creation/update is delegated to the geography-owned `development-buildings` transaction port. It checks developer/project scope and project/child versions and locks the project before the building. Inventory appends its project audit/outbox in the shared transaction; canonical building ownership remains geography. Phase, individual-offer and publication tables are registered to inventory in modules.json.
