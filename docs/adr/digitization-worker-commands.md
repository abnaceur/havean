# API-owned coordinator commands

The existing API now owns authenticated internal stage lease, renewal and CPU preparation routes. The worker must call these ports through contracts; it cannot import API internals, supply roles, read arbitrary object keys, grant itself evidence access or publish output.

`DIGITIZATION_COORDINATOR_KEY` is a separate 32-byte hex credential. Unconfigured, malformed or reused SESSION_KEY configuration disables these ports with 503. The notification/search service credential is not an engine credential. Requests bind method, full route, canonical body and a timestamp within 60 seconds using an engine-specific HMAC purpose. Runtime setup/rotation/distribution is unfinished; no deployment credential was committed or default execution enabled.

On every command, the API reconstructs the initiating actor's actual active agency roles/profile from PostgreSQL. An actor-scoped transaction then checks target/evidence authority, immutable run creator, source revision, stage version or execution/fencing token, cancellation, deadline and lease expiry. This preserves processing after a browser session closes while denying revoked memberships/assignments/grants. Service authentication alone cannot establish a human role or resource grant.

CPU preparation selects an immutable source snapshot and rechecks explicit document-processing access. Its fingerprint includes workspace/org, revision, asset/version/purpose/hash/size/MIME/decoder state and versioned profile. Ambiguous asset bindings are rejected. The returned typed request contains opaque IDs and content metadata, never provider paths, signing keys or publication authority. CPU/scratch limits are capped by the run's recorded allocation. Object transfer and processing happen outside this transaction; authority must be checked again before committing results.
