# Personal export and deletion requests

P: Identity owns `account_deletion_requests` and the versioned active-to-deletion-requested account transition. The consumer uses its BFF session. No client-supplied user ID can select a different export or deletion target. Organization/staff access does not broaden a personal export.

P: `GET /me/export` uses an explicit field whitelist across own profile, memberships, preferences/activity, saved homes/searches, inquiry/viewing/conversation/sent-message records, service/support/maintenance requests, owned inventory/media metadata and tenant bookkeeping. Ownership predicates accompany RLS. Session/token material, object-storage keys, mail payloads and internal notes are excluded. Personal property addresses require ownership. Monetary values and message sequences are strings. One SQL statement provides a consistent snapshot. Each category has a 2,000-record online limit; an oversized category fails the entire response with `EXPORT_LIMIT_EXCEEDED`, directing the member to support for a complete copy. No partial export is silently represented as complete.

P: Deletion requires the current profile version, idempotency key and exact confirmation phrase. A restricted database function binds the target to `actor_id()`, locks that profile and the optional-delivery user lock, creates one request, changes account state, revokes every Haven session, deactivates memberships, disables optional channels/history consent, pauses searches and cancels queued/failed optional digests atomically. A crashed processing digest remains available only for truthful receipt reconciliation: inactive-profile checks prevent any new send. The API appends audit/outbox in the same transaction. Provider sign-in cannot reopen a profile whose state is no longer active.

P: This function is an explicit identity-to-engagement integration port for disabling user-owned activity during the identity transition. It changes no charge, payment, allocation, deposit, reversal, lease or immutable audit row. Its temporary privileged profile update is confined to the already verified own target and restores the prior transaction setting before returning. Runtime callers have only the narrow function, not arbitrary deletion-request mutation permission.

P: Retention policy version 1 classifies optional activity, profile/contact/conversation/request data, posted bookkeeping/reversals, immutable audit/request history and identity-provider account management. Submitted deletion is a request awaiting review, not proof of completed erasure. No jurisdiction-specific retention duration is invented. Data with open obligations and posted bookkeeping stays intact for authorized retention review. The UI explains access loss before confirmation and keeps the receipt visible after clearing account caches. The identity-provider account is managed separately; all Haven sessions end immediately.
