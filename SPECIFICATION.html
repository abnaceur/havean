Build an English-language real estate platform whose consumer information architecture, interaction patterns, screen composition, and business capabilities closely reproduce the mobile web experience at https://m.ke.com/bj/. 1 Architecture decision

Use a TypeScript monorepo with a modular NestJS backend, a Next.js consumer application, a Next.js operations application, and asynchronous workers. PostgreSQL is the authoritative datastore. Search, notifications, image processing, and analytics are projections or integrations, never the source of property availability or permissions. Start as a modular monolith with separate worker processes. Extract services only after measured operational needs justify it.

1.1 Runtime boundaries

Browser -> HTTPS reverse proxy -> consumer or operations Next application -> Nest API -> PostgreSQL. Browser authenticated mutations go through a same-origin backend-for-frontend session layer. Tokens remain server-side in encrypted session storage; the browser receives Secure, HttpOnly, SameSite cookies. API validates issuer, audience, expiry and authorization. Next does not implement parallel business rules or directly mutate the business database.

API transactions write business changes and outbox events together. A dispatcher sends outbox jobs to workers. Workers maintain public search documents, media variants, email delivery and aggregate analytics. Workers can retry, so every side effect needs a deduplication key. WebSocket connections authenticate and authorize each conversation; reconnection recovers persisted messages by sequence number.

Run public and operations apps on separate configured hostnames, API behind the reverse proxy, identity on an auth hostname and assets on an assets hostname. Hostnames remain environment values until supplied. No database, search administration endpoint, cache or object-storage administration console is publicly reachable. Staging and production have separate databases, buckets, identity realms, secrets and provider accounts.

3.1 Users and roles

Visitor can see published public information. Consumer can manage only their own favorites, alerts, inquiries, conversations and bookings. Owner can manage owned property submission drafts and explicitly granted private documents. Agent can update listings and leads assigned to them within their agency. Agency manager can assign their agency's staff and inventory. Developer can manage their organization's developments. Property manager can access only granted buildings/units and management records. Tenant can access only their linked lease, charges and maintenance requests. Vendor can manage own renovation profile/quotes. Moderator reviews listings and credential submissions. Support can handle cases with least-privilege data access. Editor can curate content. Platform admin manages configuration and permissions; financial corrections require an explicit finance permission, not just agent membership.

Permissions are server-side action/resource checks, combining identity, agency or management organization, ownership/assignment, and workflow state. An organization_id supplied by a client never grants membership. Cross-organization modifications and private reads return 404 or 403 consistently. Public read models contain only deliberately published fields, including approved agent contact details. Private phone numbers, exact occupied-unit addresses, identity evidence, tenant information, notes and ownership documents are excluded from public serializers and search indexes.

3.2 Market configuration

Default interface is English. Default sample dataset is English-labeled Beijing with CNY, metric areas and Asia/Shanghai property viewing time; this preserves geographic context without assuming a UAE launch. User profile locale may be en-GB initially; currency is the property's currency and is never inferred from interface language. Store IANA time zones, UTC instants and decimal area. Make country, cities, currency, rent period, measurement units, tax/ownership labels, mortgage interest settings and required credential fields configurable. UAE deployment is an additional market configuration, not silent replacement of Beijing semantics. Add Chinese names/transliterations as optional searchable aliases, not visible untranslated interface copy.

4.1 Workflow states

  • Listing: draft -> submitted -> under_review -> published; review may reject with reasons. Published -> paused, sold/leased, expired or archived. A rejected draft can be corrected and resubmitted. Owner edits to published core facts create a pending revision; approval swaps the public version atomically. Moderators cannot publish incomplete or unverified required data. Each transition writes an audit event and outbox event.
  • Credential: pending -> under_review -> approved/rejected -> expired or revoked. Public verification badge derives from a currently valid approved record.
  • Lead: new -> assigned -> contacted -> qualified -> viewing -> offer/discussion -> won/lost. Reassignment is audited. A lead marked won does not automatically settle money or prove legal completion.
  • Viewing: requested -> confirmed -> completed/no_show/cancelled. Booking uses a transactional overlap check and idempotency; store UTC and render property-local time.
  • Lease: draft -> active -> ended/terminated. Activation requires a granted unit and tenant, dates and valid monetary terms. Activation atomically blocks incompatible new rental publication. Public listing withdrawal and lease activation cannot diverge silently.
  • Charge/payment: draft -> posted -> reversed. Posted rows are immutable. Reversals preserve original entries; deposits remain separately tracked liabilities. Recorded payments are bookkeeping evidence, not transfers of funds.
  • Maintenance: open -> triaged -> assigned -> in_progress -> resolved -> closed/reopened. Tenant only sees their authorized unit and sanitized status updates.
  • Renovation quote: requested -> assigned -> contacted -> quoted -> accepted/declined/closed. Acceptance records interest; it does not sign a contract or charge a card.

Selected facets persist on refresh and browser Back. Price presets come from market configuration. Map pins use coarse public positions, clustering and synchronized selection; exact private unit coordinates never leak. Recommendations start with documented deterministic city/category/availability rules, freshness and curated boosts; no opaque AI dependency. 6.2 Agents and agencies

Agent onboarding collects public profile and private credential data separately. Admin validates credentials and expiry before verification display. Agency manager invites staff and assigns roles; agent cannot self-approve or edit another agency. Assignment changes affect listing permissions and lead visibility immediately. CRM supports filtered queues, detail/timeline, contact status, notes, ownership reassignment and export of permitted fields. Viewing calendar handles availability, travel buffers as configurable policy, cancellation, reschedule and duplicate reservation prevention. Public agent statistics derive from approved events, with definitions and an 'unverified' fallback rather than fabricated claims.

6.3 Owners and property inventory

Sell/rent submission has location/community, property facts, proposed price/terms, media, contact verification and final review. Save per-step drafts and preserve them on login return. Private ownership evidence is optional in draft and required only by configured publication policy. Owner consents to public fields, selects permitted contact visibility, and sees assigned agent/review status. Manager/agent can prepare listing revisions; core facts cannot change on public pages before moderation when review is required. Listing expiry, renew, pause and sold/leased transitions invalidate feeds and search. Draft content and internal rejection notes are never indexed.

6.4 Development and commercial inventory

Developments distinguish project, phase, building, floor-plan type and offered unit inventory. A development card may report a range per area or a starting total price, so price basis is explicit; no multiplying an unknown area to invent a total. Show unavailable/sold-out floor plans and inventory timestamp. Developer permissions are scoped. Commercial offers reuse identity/media/location infrastructure but have their own criteria and price basis, including area/day/month/year where configured. Do not sum a monthly rent listing with yearly rent results without explicit normalization and visible billing-period labels.

6.5 Property management extension

Build a separate operations and tenant experience over the same canonical units. Management grants establish which organization can manage which units and owner data. Lease creation, activation, renewal and ending have validated dates, rent periods and deposit terms. Monthly charge generation is idempotent by lease/period/type and excludes out-of-term leases. Payment records support partial payments, allocation, overpayment credits and reversal; amounts remain exact decimals, currencies match, allocations cannot exceed available amounts. Deposits stay distinct from rent revenue and have a movement history.

Initial scope records payment evidence and balances; it does not hold funds, transfer money or claim certified trust accounting. Record who entered payment evidence and its source. Basic statements report charges, allocations, payments, deposits and reversals separately; reconcile totals to source entries. Add full accounting/export integration only through a separately defined financial contract. Maintenance supports photos, assignment, urgency, status and tenant-safe comments. Owner statement and tenant statement access are different grants; downloading another lease's document must fail.

6.6 Communications and service requests

An inquiry is a persisted lead linked to listing/development/provider and its assigned destination. Deduplicate network retries with idempotency; guest inquiries require validated contact and anti-abuse limits. Booking cannot succeed for a withdrawn listing. Persist messages before acknowledging; support client-generated message IDs, read cursors, reconnect replay and attachment authorization. Escape message text, prohibit executable HTML, and rate-limit sends. Automated notifications are templated in English and honor opt-outs, except strictly necessary transactional events. Support cases can be assigned, escalated and resolved; private support notes stay out of public chat.

6.7 Mortgage calculation

Offer equal-payment amortization and equal-principal methods as proposed baseline methods; confirm reference calculator inputs during visual audit. For equal payments with principal P, monthly rate r = annual nominal rate/12 and n months, M = P*r/(1-(1+r)^(-n)); when r=0, M=P/n. Compute schedules with decimal arithmetic, disclose nominal-rate assumption and rounding, and adjust final payment to clear principal. Down payment cannot exceed property price; principal and term must be positive; rates cannot be negative. Show monthly payment, total interest, total repaid and downloadable schedule. Market-specific tax and lender fees default to excluded and display that fact; results are estimates, not lender approval. Fixture: P=120000, rate=0, term=120 months yields 1000 per month, zero interest and zero closing balance.

7 Security and operational quality

Minimum release gates are proposed engineering targets, not benchmark claims. Protect session cookies with CSRF/origin validation on mutations, rotate sessions after authentication, restrict redirect targets, and test logout and revoked membership behavior. Require MFA for platform staff; role grants are audited. Rate-limit login handoffs, inquiries, uploads, downloads and message sends with consistent 429 feedback. Use CSP, safe escaping, MIME validation, request size limits, parameterized queries and private buckets. Scan dependencies/secrets; resolve exploitable high/critical findings before release. Logs must redact tokens, private contacts and document URLs. No default administrator password is committed or displayed; bootstrap through a one-time invitation/secret mechanism.

Accessible interface: WCAG 2.2 AA target, keyboard-reachable controls, visible focus, semantic labels, modal focus return, 44-pixel touch targets, contrast and reduced-motion handling. Test translated overflow at 320-pixel width. Color is never the only status indicator.

Performance targets: on a declared production-like fixture of 100000 listings and 1000 concurrent browsing sessions, document the hardware and request mix; public search p95 under 500 ms, detail API p95 under 300 ms, errors below 1 percent during a 10-minute test after warmup. Use a smaller 100-session smoke gate during development. Browser LCP <=2.5 s, INP <=200 ms and CLS <=0.1 are launch targets on representative mobile devices; lab reports and later field monitoring are separate evidence. No claim of meeting a target without a recorded run. Resize images, lazy-load noncritical media, SSR meaningful public content, cache public reads and inspect query plans.

SEO: unique English metadata, canonical URLs, accurate structured data where appropriate, city/category/detail sitemap, robots exclusion for account/ops/tenant and controlled indexing of filter permutations. No indexing of private data or infinite faceted URLs. Analytics events are defined and consent-aware: listing_impression, listing_view, favorite_added, inquiry_submitted, viewing_requested and quote_requested, deduped by documented keys. Do not record typed private messages or identity documents in analytics.

Logs/metrics: request correlation, API latency/error rate, outbox age, queue retries/dead letters, search lag, media failures, email delivery and database resource usage. Distinguish liveness from readiness; production readiness must fail when required migrations/database access are unavailable. Alert on outbox lag above 60 seconds sustained for 5 minutes and repeated delivery/media failures; tune from operations data.

Proposed backup target: database point-in-time recovery with <=15-minute RPO and <=4-hour RTO, versioned object storage, encrypted off-host backups and quarterly restore drills. Keycloak realm configuration and identity database need their own protected backups. Cache and search can be rebuilt. Until WAL archiving is configured and recovery verified, do not claim 15-minute RPO. Deploy with immutable image digests, expand/contract migrations, preflight checks and a database-aware rollback plan. Never promise that restoring a previous app image safely reverses arbitrary schema changes.

9.1 Minimum test policy

Every functional task gets at least one automated success assertion and one relevant failure/boundary assertion. Every permission-bearing task also gets an unauthorized or cross-organization integration assertion against the actual application/database role. Every new visible interaction gets one browser or component interaction test; every screen gets loading/empty/error handling and visual evidence at mobile width. Pure document/configuration tasks use a reproducible contract validation instead of meaningless unit tests. Finance and booking concurrency add invariant/race tests because a happy path cannot establish correctness.

Use fixed clocks, seeded deterministic fixtures and independent users/organizations. Database integrations exercise migrations on PostgreSQL/PostGIS, not mocked in-memory storage. Queue tests exercise real pinned service containers. Unit tests are reserved for state transitions, parsing, formulas and transformations. E2E runs local integrated services, not benchmark scraping. Provider adapters use protocol fixtures plus a staging connectivity check for configured production providers. Do not depend on paid external calls in ordinary CI.

Proposed root scripts that Codex must implement: pnpm lint, pnpm typecheck, pnpm build, pnpm test:unit -- <test-path>, pnpm test:integration -- <test-path>, pnpm test:e2e -- --grep <task-id>, pnpm test:visual -- --grep <screen-id>, pnpm task:validate and pnpm check:release. Commands are a target interface, not commands proven to exist in this handoff. Avoid treating command exit zero as sufficient: record asserted business outcomes. PR CI runs affected tests and schema/contract checks; milestone CI runs integrated critical journeys; release CI runs the full declared gate once after final changes.

9.2 Resume and blocker behavior

For a task set in_progress, checkpoint before long tool calls. On completion record changed files, exact commands/exit results, test assertions, screenshot paths, commit SHA and any remaining limitation under evidence/tasks/ID.md. Update TASKS.json, its readable copy and PROGRESS.md in the same change. Preserve unrelated user edits and never reset a repository to manufacture a clean state.

On failure, diagnose and fix before broadening work. On a true external blocker mark only affected tasks blocked, state exact missing input and continue independent ready tasks. Reference access cannot be invented; provider credentials cannot be fabricated; production data cannot be substituted with synthetic fixtures without clear demo labeling. The coding runtime has context/session limits: 'continuous' means continuing through available ready work and writing a reliable checkpoint for automatic or manual resumption, not promising indefinite background execution. This package specifies development; it does not start an automation or deploy a live platform.

10 Definition of release completion

Marketplace release requires all marketplace tasks done, each observed/retrieved requirement mapped to evidence, all V screens either verified or explicitly accepted as a documented deviation, all critical journeys passing, and no known critical/high exploitable security defect. Exact benchmark parity cannot be claimed while unverified screen states remain. Management release separately requires its role-isolation, charge-generation, allocation/reversal/deposit and statement reconciliation evidence.

Required complete journeys: anonymous resale filter/detail -> sign-in -> favorite; owner draft -> private evidence -> submit -> moderator approval -> public listing; rental inquiry -> agent contact -> confirmed viewing -> cancellation/reschedule; developer floor-plan publication -> buyer inquiry; agency membership -> assignment -> scoped CRM; commercial inquiry; renovation quote; mortgage schedule; manager lease -> charge -> payment allocation -> tenant statement -> reversal; tenant maintenance -> manager resolution; complaint -> support resolution; search withdrawal and queue replay; restore and application rollback.

Operations completion includes working HTTPS staging with synthetic fixtures, production-ready container configuration, environment reference, seed/backup/import instructions, verified restore and rollback reports, and a provider/hostname readiness checklist. Production launch needs actual inventory, authorized domain/provider access and launch configuration. Do all reversible setup and verification before reporting these specific external inputs; do not ask for routine implementation approval. Do not claim production completion from a local demo.
