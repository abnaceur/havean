# I05 — protect published revisions

Published core edits are stored in a private pending revision with a base listing version. Authors supply a reason; the public title, price and other facts remain unchanged until an independent moderator verifies and approves the revision. Rejection preserves the current public revision. Concurrent proposals, stale listing/revision versions, withdrawn properties and self approval are denied. Submission and decisions use idempotent API transactions and emit audited outbox events.

Operations authors can propose title/price changes; moderators can approve or reject with reasons in the verification queue. The API also supports pending description, features, furnishing and availability changes. Approved changes update the listing revision and search projection.

Evidence: four real database assertions plus five live canonical contract checks passed (`evidence/revisions-integration.log`). Two desktop/mobile browser journeys passed (`evidence/revisions-browser.log`): public and search prices remain original while pending, both become the exact approved decimal price, replay creates one history event, and a second rejected proposal preserves the approved public version. Agent approval is denied. Workspace types, lint and 123-operation generated contracts pass.
