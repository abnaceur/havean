# F13 — Readiness, request tracing, redaction and operational metrics

Liveness is independent of PostgreSQL. Readiness requires a reachable database and every migration file recorded in its journal; missing migrations or database outage fail with sanitized 503 `NOT_READY`. Pools have bounded connection timeouts and handle idle connection failures without terminating the API process.

Every API response has a generated request ID; completion/error records use route templates and exclude request bodies, cookies, authorization and query strings. Structured redaction covers nested secret/contact fields and embedded emails/bearer tokens. Bounded route metrics count requests, failures and durations. Administrator-only `/health/metrics` exposes outbox pending/processed/age/dispatch counts and actual BullMQ job counts from an authenticated internal worker endpoint. Missing queue metrics are explicit nulls.

Verification:

- `readiness-outage.log`: stopped the isolated test PostgreSQL container. Liveness remained 200; readiness returned 503 `NOT_READY`; readiness recovered to 200 after restart. Development PostgreSQL was untouched.
- `readiness.test.ts`: real DB connectivity, all migrations, deliberate missing migration and real refused connection checks passed in both clean integration runs.
- `observability.spec.ts`: healthy endpoints/request IDs; anonymous metrics 401; consumer 403; admin actual queue/outbox values, on desktop and mobile. Full run `isolated-reset-second.log`: 34 browser assertions passed.
- `observability.test.ts`: nested/embedded token and email redaction plus bounded tracing assertions passed; latest unit log records 19 checks including reference validation.

No production collector or alerting deployment is claimed; those are later release tasks.
