# F06 — identity and server sessions (verified)

Implemented actual Keycloak authorization-code login with S256 PKCE, signed token issuer/audience verification, nonce/state/expiry validation, permitted application origins, relative return paths, encrypted server-side token storage, refresh, session rotation, logout and immediate account/membership checks. Browser cookies are HttpOnly and SameSite=Lax; production requires Secure cookies and HTTPS origins.

`tests/e2e/sessions.spec.ts` exercises real provider login, a second login rotating the identifier, denial of the old identifier, database-expired session denial, provider logout, server-session removal, and return to the provider login page. `tests/e2e/journeys.spec.ts` additionally verifies invalid state, external redirect rejection and token exclusion from browser JavaScript. Both desktop and mobile projects run in the Docker test profile.

Staff authorization rejects verified access tokens below ACR level 2 in every environment. Both application login handoffs request level 2. The `haven-browser` provider flow requires username/password, then role-scoped OTP with a level-of-authentication condition. A successful OTP grants level 2; password-only consumer sign-in does not grant staff access. The condition is not mapped to a password-only execution.

`scripts/identity-policy.mjs` defines the importable flow, and `scripts/identity.mjs` configures existing local realms idempotently. Generated local staff personas have unique random TOTP secrets, stored only in ignored files. Production users enroll their own authenticators; development fixtures are prohibited in production.

5 October 2026: eight targeted desktop/mobile checks passed in Docker, including wrong-OTP denial, password-only challenge, successful OTP staff authorization, session lifecycle, invalid state/redirect and browser token exclusion. Keycloak rejects reuse of successful OTP codes; the test helper waits for the next time window instead of disabling that protection. Full output: `evidence/identity-tests.log`.

Provider configuration follows the [Keycloak administration guidance](https://www.keycloak.org/docs/26.4.7/server_admin/) and the pinned provider's conditional-role/LoA implementations.
